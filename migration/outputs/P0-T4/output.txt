# P0-T4 — Independent review of the Slint RSS spike (`migration/P0-T2`)

Reviewed: `git diff main...migration/P0-T2` plus full reads of
`spike-slint/src/main.rs`, `spike-slint/Cargo.toml`, `spike-slint/ui/app.slint`,
`spike-slint/MEASURE.md`, and cross-checks against
`src-tauri/Cargo.toml` (on the branch) and `spike-slint/Cargo.lock`.

Diff scope: `.gitignore` (+1), `migration/tasks.json`, and a new self-contained
`spike-slint/` package (Cargo.toml, Cargo.lock, build.rs, src/main.rs,
ui/app.slint, MEASURE.md). Nothing in `crates/` or `src-tauri/` is touched.

## Verdict summary

The spike is honest. The allocation is real, the meter is fed by a real
`/proc/self/status` read, and — most importantly — **the spike explicitly
declines to make the RAM-savings claim it was chartered to investigate**,
because the matched Tauri post-allocation point could not be captured. That is
the correct call under this project's "never present a fabricated number as
measured" rule, and it is stated in both `MEASURE.md` and the `tasks.json`
notes. My findings below are limitations that must be recorded before anyone
*derives* a webview-savings number from these figures — not fabrications in
what was actually committed.

## Findings (most important first)

1. **The idle comparison is app-vs-app, not toolkit-vs-toolkit, and
   `MEASURE.md` does not warn about this.** `MEASURE.md:104-111` warns only
   about (a) the missing post-allocation point and (b) counting WebKitGTK child
   processes. It never warns that the two binaries are not comparable
   workloads: the Slint side is a 90-line window with two buttons and a
   rectangle meter, while the Tauri side (`src-tauri/Cargo.toml` on this
   branch) links `tokio` with `features = ["full"]`, `sqlx` (postgres +
   rustls), `reqwest`, `sysinfo`, `jsonwebtoken`, and `chrono` — plus the full
   React bundle. A meaningful part of the 92428 kB → 198332 kB idle gap is
   Tokio worker-thread stacks, the TLS/HTTP stack, and app state, not
   WebKitGTK. Anyone reading only the "Measurements from this worktree" section
   could easily attribute the whole ~106 MB main-process gap (or the ~358 MB
   tree gap) to the webview. **This confound should be stated as explicitly as
   the missing-datapoint one is**, and the eventual P6 validation should
   compare like-for-like (e.g. Slint app with the same core crate linked in, or
   an empty Tauri window) before any causal claim.

2. **Neither the Slint rendering backend nor the number of runs is recorded,
   so the 92428 kB idle figure is not reproducible.** Slint 1.17 selects a
   backend/renderer at runtime (winit + femtovg by default, software/skia
   otherwise), and on GNOME/Wayland the GL driver's mappings are a large and
   highly machine-dependent share of a ~90 MiB idle RSS. `MEASURE.md:113-126`
   records the build and launch commands but not `SLINT_BACKEND` /
   `SLINT_RENDERER`, the GPU driver, or the desktop session. It also says
   "repeat runs are useful" (`MEASURE.md:104-105`) but records exactly one
   sample per binary with no variance. Both should be captured before these
   numbers are cited anywhere downstream.

3. **`Clear buffer` does not lower RSS, but `MEASURE.md` implies it resets
   state for a repeat measurement.** `src/main.rs:51` calls `Vec::clear()`,
   which sets the length to 0 and *keeps the capacity* — the 50 MiB stays
   mapped and resident. `MEASURE.md:35` says "Click **Clear buffer** before
   exiting if repeating a run", which invites a reader to click clear, re-read
   `VmRSS`, and record ~143 MB as a new "idle" baseline. The UI reinforces the
   illusion: `used-text` drops to `0 B` and `buffer-text` reverts to "No buffer
   allocated" while RSS is unchanged. This is the one place the spike's display
   and its actual memory state disagree — a `shrink_to_fit()` (or replacing the
   `Vec` outright) would make the button mean what it says, and would also be a
   useful teaching point for the real app.

4. **Both sides use the default `release` profile, but that fact is inferred,
   not documented.** Verified: `spike-slint/Cargo.toml` declares no
   `[profile.release]`, and neither does `src-tauri/Cargo.toml` on this branch,
   so both are plain `cargo --release` (same opt-level, same LTO setting, same
   system allocator — no jemalloc/mimalloc on either side). So the
   apples-to-apples check on **build profile passes**, and there is no
   allocator confound. Worth stating in `MEASURE.md` explicitly, since a later
   `[profile.release]` tweak on either side would silently invalidate the
   comparison.

5. **`--auto-load-after` argument parsing fails silently on malformed input.**
   `src/main.rs:30-36` collects args, uses `windows(2)`, and drops the flag
   entirely if it is the last argument or if the value does not parse as `u32`.
   A typo yields a run that never allocates, and the operator would only notice
   via the UI text. Low impact given `MEASURE.md:126` records the
   `Rust Vec<u8>: 50.0 MiB` UI confirmation as part of the procedure, but a
   hard error would be safer for an unattended measurement harness.

6. **Nit: the meter is pinned at 100% and the label reads "50.0 MiB of
   10 MiB".** `src/main.rs:74` clamps to `RAM_CAP` for the bar while
   `used-text` (`ui/app.slint:40`) shows the unclamped size against a hardcoded
   "of 10 MiB". Harmless in a spike whose whole point is exceeding the cap, but
   the production pane will need over-cap handling rather than this mismatch.

7. **Nit: `spike-slint` declares its own `[workspace]`** (`Cargo.toml:12`), so
   it is excluded from the repo's build/CI graph and can rot silently. Fine and
   arguably correct for a throwaway spike; just be aware it will not be caught
   by CI, and it ships a 6172-line `Cargo.lock` into the tree.

## Explicit answers to the four review questions

1. **Apples-to-apples?** *Partially.* Same build profile (default release on
   both — verified), same workload definition (50 MiB), same measurement
   command (`grep '^VmRSS:' /proc/$PID/status`). But only the **idle** point
   exists on both sides; the Tauri post-allocation point is missing
   (`MEASURE.md:135-139`) and this is disclosed, not hidden. The unmitigated
   asymmetry is application scope (finding 1) and unrecorded
   backend/environment (finding 2).

2. **Real allocation or faked meter?** **Real, and corroborated by the
   numbers.** `src/main.rs:42-46` does `bytes.resize(BUFFER_SIZE, 0)` on a real
   `Vec<u8>` and then writes to every 4096th byte to force residency; the
   displayed RSS comes from parsing `VmRSS` in `/proc/self/status`
   (`src/main.rs:9-15`), not from an internal counter. The recorded delta
   confirms it: 143632 kB − 92428 kB = 51204 kB = exactly 50.0 MiB. **No
   CLAUDE.md violation — no fabricated number is presented as measured
   anywhere in this branch.** The spike also writes no files at all, so it does
   not violate the vault-only rule either.

3. **Is the savings conclusion supported?** **No conclusion is drawn, which is
   the correct outcome.** `MEASURE.md:108-111` and `MEASURE.md:141-142` state
   plainly that no RSS-savings claim is made because the two apps were not
   measured at both matched points; `tasks.json` repeats this in `notes.done`
   and `notes.missing`. Nothing conflates binary size or allocator differences
   with webview removal. The risk is prospective, not present: the raw idle
   numbers are sitting in the file and, absent finding 1's warning, invite a
   later reader to compute a bogus "webview costs 106 MB" delta.

4. **Slint API misuse / unrepresentative build?** **None found.** Release build
   is used and required by the doc (`MEASURE.md:16`). `slint = "1.12"` resolves
   to **1.17.1** in the committed `Cargo.lock`, matching the environment
   recorded in CLAUDE.md. The `Timer` is bound to a named local
   (`src/main.rs:56`) that outlives `window.run()`, avoiding the classic
   drop-on-scope-exit bug; the window is held via `as_weak()` inside the
   callback, so there is no `Rc` cycle leaking the window. The 250 ms period
   correctly matches the app's 4 Hz cadence. `build.rs` + `include_modules!` is
   the standard Slint wiring. No debug-only allocations or dev-mode paths.

## Bottom line

Nothing here fabricates a measurement or overstates a result, and the one
question the spike was chartered to answer is left honestly unanswered. Before
this branch's numbers are reused in P6 validation, findings 1–3 should be
folded into `MEASURE.md` (scope confound, backend/run-count, `clear()`
semantics). None of those is a correctness defect in the committed code.

VERDICT: PASS
